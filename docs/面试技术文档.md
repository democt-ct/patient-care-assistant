# 患者照护助手 — 面试技术文档

> **项目现状**：产品已从初期的「RAG 医疗问答助手」演进为「就诊后照护协同助手」——前端呈现为健康工作台（健康概览 / 照护计划 / 智能问诊），核心业务是「医生发布照护计划 → 患者执行待办 → 协调员处理求助」的可追溯闭环，AI 问诊只是其中一个模块。
>
> 一句话：一个面向患者的就诊后照护协同助手，在照护闭环之上叠加 AI 智能问诊（自然语言查病历/就诊记录、图片理解报告、多轮对话记忆、语音播报），核心设计是「确定性安全 + 自研 LLM 编排 + 分层记忆」。
>
> 本文档按面试口径组织：先讲全貌与核心链路，再逐个模块讲「概念 / 为什么 / 好处 / 不这样做会怎样」，最后是追问速答与深挖方向。
> 文中数字与代码一致：PostgreSQL 17 张表、MCP 6 个工具、四层记忆体系。
>
> **星级说明**：★★★ 核心必会（建议背熟）｜★★ 高频必问｜★ 了解即可

> **面试口径提示**：开头 30 秒先讲"这是照护协同产品，AI 问诊是模块之一"，再展开技术设计；避免把项目说成纯医疗问答助手（那是早期形态）。

| 模块 | 一句话 |
|------|--------|
| **中间件层** | 鉴权、限流、审计三道关卡，患者 token 与路径/参数中的 patient_id 必须一致 |
| **MCP 工具层** | 6 个工具（4 个患者数据查询 + 2 个身份认证），LLM 编排暴露其中 5 个 |
| **编排引擎** | plan-then-execute 而非 ReAct：意图识别 → 多候选规划 → 本地共识投票 → 执行 → 回答 |
| **安全体系** | 生成前确定性安全门 + 三级分诊，生成后幻觉检测 + 药物相互作用 + 过敏比对 + 免责声明 |
| **记忆系统** | 四层：事实、短期工作、长期摘要、知识记忆，各司其职 |
| **RAG 检索** | ChromaDB 向量 + 关键词 + 元数据 + 时效四路融合，可选 Cross-Encoder 重排序 |
| **LLM 降级** | 主备双模型，模型内部 3 次指数退避重试，视觉/TTS 同样级联 fallback |
| **照护计划** | 模型只读查询/解释，生成草案后由医生审核发布、患者确认执行，职责边界清晰 |
| **可观测性** | trace_id 贯穿全链路，指标用路由模板防标签爆炸，患者/会话 ID 哈希脱敏 |
| **评估系统** | 三维评分（意图+关键词+安全），版本化落库，答案只存 SHA256 指纹不存原文 |

### 核心亮点 Top 5（30 秒电梯陈述）★★★

1. ★ **安全优先的双保险**：生成前用确定性规则拦截停药/剂量/自伤等高风险请求，生成后再做幻觉检测、药物相互作用、过敏比对——安全判断不依赖单一概率模型。
2. ★ **自研 Plan-Then-Execute 编排**：一次规划生成 3 个候选工具计划，本地共识投票选最优，主链路仅 3 次 LLM 调用，延迟可控、行为可审计。
3. ★ **四层记忆体系**：事实 / 短期工作 / 长期摘要 / 知识四层分离，热路径走 Redis、事实与摘要落 PG、知识进 ChromaDB，异步抽取不阻塞请求。
4. ★ **照护计划人工闭环（当前产品的核心业务）**：Agent 只负责理解、检索与解释，草案生成后必须医生审核发布、患者确认，临床动作不交给模型自动执行。
5. ★ **生产级合规设计**：审计日志、敏感字段脱敏、90 天数据保留、路由模板指标、评估只存指纹，医疗数据「宁可慢一点，不可错一点」。

## 三、核心链路 ★★★

### 一条请求的完整路径 ★★★（建议按阶段背出流程）

```
用户提问 "我最近的血糖怎么样"
  → Logging 生成 trace_id
  → RateLimit 令牌桶放行（60 次/分钟/IP）
  → PatientDataGuard 校验 auth_token 与 patient_id 一致性，异步写审计日志
  → API 端点：恢复 Redis 短期记忆、解析患者身份、加载事实/长期/知识上下文
  → 安全门扫描（确定性规则，不调 LLM）：命中停药/剂量/自伤 → 直接返回安全话术
  → 三级分诊（规则）：EMERGENCY → 引导就医并升级；URGENT → 建议 24h 内就诊
  → 意图识别（关键词先筛 + LLM 精判）：判定 medical_records_query
  → 直接路径判断（记忆记录/召回等场景可跳过规划，直接回答）
  → 规划候选生成（LLM 一次调用）：生成 3 个候选工具调用计划
  → 共识选择（本地加权投票，无 LLM）：confidence + 序列频次 + 首工具频次 + 意图重叠
  → 工具执行：get_medical_records 查 PG（患者数据工具自带 token 约束）
  → 回答生成（LLM 一次调用）：融合病历 + 记忆 + 知识库上下文
  → 生成后校验链：过敏比对 → 风险建议 → 药物相互作用 → 幻觉检测 → 免责声明
  → 置信度评估 + 持久化会话消息 + 异步触发长期记忆抽取
  → 返回 SSE 流式响应（status/intent/planning/tool_execution/token/done，含执行步骤摘要）
```

### LLM 调用点全景 ★★★

| 调用点 | 是否主链路 | 说明 |
|--------|-----------|------|
| 意图识别 | 主链路（1 次） | 关键词规则先筛，LLM 只处理歧义，uncertain 自动降级关键词兜底 |
| 规划候选生成 | 主链路（1 次） | 一次调用产出 3 个候选计划 |
| 回答生成 | 主链路（1 次） | 融合工具结果、记忆、知识库、安全约束 |
| 图片理解 | 按需 | 有图才调视觉模型，额外 1.5-3s |
| 查询改写 | 按需 | RAG 链路把口语转术语，失败回退原文 |
| 幻觉检测实体抽取 | 按需 | 回答涉及患者数据时抽取实体与工具结果比对 |
| 长期记忆抽取 | 异步 | 业务画像/会话画像，置信度分级，不阻塞请求 |

> ★ 主链路稳定为 3 次 LLM 调用；其余按场景按需触发，这是「延迟可控」的关键，也是追问高频点。

### 真实延迟时间线（参考值）★

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 中间件开销 | ~2ms | 令牌桶检查 + JWT 解析 + 审计入队 |
| 会话恢复 + 记忆加载 | ~15ms | Redis GET + PG 画像/上下文查询 |
| 安全门 + 分诊扫描 | ~2ms | 纯规则匹配，不调 LLM |
| 意图识别 LLM | ~600ms | 1 次 API 调用 |
| 规划 + 共识 | ~800ms | 1 次 LLM 生成 3 候选 + 本地投票 |
| 工具执行 | ~30ms | PG 查询患者病历（走索引） |
| 回答生成 LLM | ~1200ms | 融合多源上下文生成 |
| 生成后校验 + 持久化 | ~80ms | 规则比对 + 异步写库 |
| **总计** ★ | **~2.7s** | 端到端用户感知延迟 |

> 注：视觉图片理解额外增加 1.5-3s，TTS 语音合成增加 0.5-1s；若启用 RAG 重排序另加数百 ms。

## 四、模块逐个说 ★★★

### 4.1 安全门（Safety Gate，生成前）★★★

**概念**：在 LLM 调用之前，用确定性规则拦截高危请求（停药建议、剂量变更、自伤倾向、紧急症状）。

**为什么这么设计**：医疗场景容错率极低。LLM 有幻觉风险，不能把安全判断交给概率模型。★ 核心论点：安全门是「宁可错杀、不可漏过」的兜底。

**好处**：零 token 消耗；高危请求被确定性阻断，可审计可追溯；规则是配置级可热更新，不依赖模型迭代。

**不这样的坏处**：如果把安全检查放在 LLM 之后，等于让一个有幻觉风险的模型去判断自己有没有幻觉——逻辑不成立，漏过就是医疗风险。

### 4.2 三级分诊（Triage）★★

**概念**：基于紧急症状词表做确定性分级：**EMERGENCY**（胸痛、呼吸困难、意识模糊等 → 立即就医/拨打 120，自动触发人工升级）、**URGENT**（24h 内就诊）、**ROUTINE**（常规咨询，正常对话）。含否定词（"没有胸痛"）与历时词（"之前有过"）识别，避免误报。

**为什么这么设计**：★ 核心区别：安全门是「不能答」，分诊是「必须引导就医」。两者配合：命中紧急症状时回答不再是知识性内容，而是带明确就医指令的升级响应，附风险提示与免责声明。

**好处**：规则先行 0 延迟；与安全门共用词表体系，维护成本低；风险信号同时写入记忆的 risk_signals 字段，供后续轮次持续关注。

**不这样的坏处**：纯靠 LLM 识别紧急症状，一旦把"胸痛"当普通问题回答，就是生死问题；且无否定词识别会疯狂误报。

### 4.3 Plan-Then-Execute 编排（而非 ReAct）★★★

**概念**：LLM 一次生成多个候选工具调用计划，本地投票选最优，再执行工具、生成回答。★ 主链路 LLM 仅 3 次调用（意图、规划、回答）。

**为什么这么设计**：ReAct 循环（思考→行动→观察→再思考）有两个致命问题：一是 LLM 可能在多轮中逐渐偏离原始意图，二是每轮调 LLM 延迟不可控。plan-then-execute 把不确定性压缩到一次规划调用。

**共识投票算法** ★（本地规则，不调 LLM）：

```
consensus_score = confidence
                + 同工具序列出现次数 × 0.35
                + 首工具出现次数 × 0.15
                + 与意图提示工具重叠 × 0.20
                − 多余工具步数 × 0.05
```

**好处**：延迟可控；计划在执行前已生成、可审计；共识机制避免单个候选计划偏航；意图提示（INTENT_TOOL_HINTS）作为先验约束工具选择范围。

**不这样的坏处**：走 ReAct 的话，复杂查询可能 5-8 轮 LLM 调用，延迟翻 2-3 倍，且中间轮次可能被幻觉误导到错误工具路径。

### 4.4 生成后安全校验链 ★★★

**概念**：回答生成后按序执行四道本地/混合校验，全部通过才返回：

1. **过敏安全比对**：从回答中提取药物名，与患者过敏史（allergy_drugs）比对，命中即警告并禁止推荐；
2. **风险建议**：把分诊风险信号（risk_signals）转成面向用户的就医建议；
3. **药物相互作用**：从工具结果提取患者在用药物组合，查相互作用规则表并追加警告；
4. **幻觉检测**：LLM 抽取回答中的药物/疾病/检查/症状/治疗实体，与工具返回的患者数据比对，无法确认的实体追加「内容核实提醒，请以医生诊断为准」；
5. 最后统一追加医疗免责声明（仅面向医疗类意图）。

**为什么这么设计**：★ 核心思路：生成前安全门挡「不能答的问题」，生成后校验链查「答出来的内容」。两者互补，覆盖 LLM 输出阶段的残余风险。

**好处**：错误内容在被用户看到前就被标注或改写；校验规则全部可单测；严格模式（strict_mode）下任何无法从病历确认的实体都会被提醒。

**不这样的坏处**：只做生成前检查，模型完全可能生成"推荐 XX 药"这类与患者过敏史冲突的内容，靠人眼发现就太晚了。

### 4.5 四层记忆体系 ★★★

**概念**：★ 四层记忆：事实 / 短期工作 / 长期摘要 / 知识。不同记忆的读写频率和生命周期完全不同，分层存储：

| 层 | 内容 | 存储 |
|----|------|------|
| 事实层 | 患者主档、病历、就诊记录 | PG（patients / medical_records / visit_records），请求期直查 |
| 短期工作记忆 | 最近 N 轮对话 + intent/topic/goal/next_action/risk_signals 等结构化字段 | Redis（24h TTL）+ PG 会话缓冲（memory_session_buffer_messages） |
| 长期摘要记忆 | 用户画像、业务画像、会话画像、偏好、关键事件 | PG 5 张表，异步抽取沉淀，extracted_at 增量更新 |
| 知识记忆 | 审核过的医疗知识块（用药指导、检查说明等） | PG（memory_knowledge_chunks）+ ChromaDB 向量索引 |

**为什么这么设计**：短期记忆需要亚毫秒读写（热路径），事实层必须强一致直查 DB，长期摘要需要异步提炼，知识块需要语义检索。混在一起会导致热点数据访问慢、冷数据污染缓存。

**好处**：热路径只访问 Redis 不碰 PG；会话消息持久化可追溯，promote 后可沉淀为长期画像；记忆抽取按事件类型分级写入阈值（关键事件 0.75 / 会话事件 0.82 / 业务事件 0.9）控制噪音；Redis 宕机自动降级内存 Mock，单次查询不受影响。

**不这样的坏处**：全部放 Redis → 宕机丢全部记忆；全部放 PG → 每请求 JOIN 查询，高并发性能崩塌；全部塞进一个 profile_summary → 画像被噪音淹没。

### 4.6 混合知识检索 ★★

**概念**：多路召回 + 融合打分。向量检索（语义相似）+ 关键词匹配（精确命中）+ 元数据过滤（医院、科室、审核状态、有效期）+ 时效性评分，四路加权融合，可选 Cross-Encoder 重排序：

```
★ final = 0.58 × vector + 0.22 × keyword + 0.12 × metadata + 0.08 × recency + 0.04 × confidence
```

**为什么这么设计**：纯向量对医学术语同义词处理好但精确匹配差（"二甲双胍"与"格华止"语义近、向量不一定近）；纯关键词精确但缺乏泛化（"血糖"漏掉"空腹葡萄糖"）。混合互补。

**好处**：权重可调、按科室可调整；查询改写（LLM，失败回退原文）把口语转术语再检索，提升命中率；重排序默认关闭，需要精度时按需开启。

**不这样的坏处**：单路检索下，精确查"2024年3月血常规报告"可能返回语义相近但不相关的结果，或纯关键词搜索漏掉同义词表达。

### 4.7 LLM 级联降级 ★★

**概念**：主模型(DeepSeek-V4-Flash) → 备用模型(Qwen3-235B)，每个模型内部 3 次指数退避重试（1s→2s→4s）。视觉模型与 TTS 引擎同样级联 fallback（外网 OpenAI 接口 → 本地 Kokoro）。

**为什么这么设计**：国内 API 网关的 RateLimitError、5xx、Timeout 不可预测。★ 级联降级把单点故障概率从 P 降到 P²。

**好处**：用户无感知——重试与切换全程在后端完成；指数退避避免雪崩重试打爆 API；本地 TTS 让医院内网无外网环境也能用。

**不这样的坏处**：单模型无降级时，高峰期 RateLimit 直接 500，用户体验是"系统坏了"而非"稍等一下"。医疗场景这种不可用不可接受。

### 4.8 照护计划闭环 ★★★

**概念**：从就诊/病历记录生成照护草案，但要经过★ **医生审核发布 → 患者确认 → 待办执行 → 状态留痕**的人工闭环；Agent 侧只有只读工具 `get_my_care_plans`（查询已发布计划、待办状态和来源依据）。

**为什么这么设计**：模型辅助理解、检索和编排没问题，但「把病历解析结果当成医嘱」是事故源头。生成规则硬约束：只生成复诊、检查、观察、处方核对类任务，不生成诊断、剂量或停药建议；草案必须医生确认后才对患者可见。

**好处**：职责边界清晰可解释（面试加分项）；每项任务带 evidence_source + evidence_excerpt（证据溯源）；支持逾期计算、延后（snooze）、求助协作单（CareCase），协调员接手处理闭环；状态事件全部留痕（care_plan_item_events）。

**不这样的坏处**：如果模型直接改任务状态或自动发布，就是"AI 下医嘱"，一旦出错责任无法界定，也不符合医疗合规预期。

### 4.9 可观测性与隐私 ★★

**概念**：trace_id 贯穿请求全链路（从中间件到每个 LLM span），Prometheus 指标用路由模板去标签化，患者/会话 ID 进 span 前做 SHA256 哈希。

**为什么这么设计**：可观测性的核心矛盾是"既要定位问题又要保护隐私"。用路由模板（如 `/api/v1/patients/{id}/records`）而非原始 URL 避免标签爆炸；用哈希而非明文避免敏感数据泄漏到日志系统。

**好处**：生产问题通过 trace_id 快速定位到具体阶段；指标基数可控；审计合规——原始患者 ID 不出现在指标与追踪系统中。

**不这样的坏处**：直接用原始 URL 做标签，每个 patient_id 一组时间序列，1000 个患者 1000 组指标，内存和查询性能迅速劣化。

### 4.10 质量评估系统 ★★

**概念**：用例单一数据源（`app/config/evaluation_cases.py`），HTTP 接口、命令行运行器、前端控制台统一取数；服务端三维评分：**意图（0.3）+ 关键词（0.4）+ 安全（0.3）**。

**为什么这么设计**：评估是质量监控不是内容审计。评分规则必须稳定可复现，所以带 `scoring_version` 与 `case_version`（对影响评分的字段做 SHA256 指纹）；历史记录存模型/提示词/知识库版本与 trace_id，用于趋势分析，但**不存原始回答**，只存回答 SHA256 指纹。

**好处**：改动用例只需改一个文件；版本化记录能回答"这版提示词改坏了哪个用例"；避免"改了代码忘了改测试预期"；隐私合规。

## 六、工程补充 ★

### 消息队列为什么没引入 ★★

当前是请求-响应同步模式，延迟要求 3 秒内返回。引入消息队列（Celery + RabbitMQ）会：
- **增加端到端延迟**：入队→消费→回调至少 200-500ms；
- **增加运维复杂度**：多一个需要监控、重试、死信处理的组件。

异步任务（记忆抽取、审计写入）用线程/APScheduler 就够了：这些是"尽力而为"的后台任务，丢失可容忍。未来若需要"可靠异步通知"（如照护计划到期提醒），再引入不迟——架构上已把异步点隔离在服务层。

### 缓存策略：缓存什么、为什么不缓存什么 ★★

| 缓存项 | 位置 | TTL | 原因 |
|--------|------|-----|------|
| 短期记忆 + 会话状态 | Redis | 24h | 高频读写，热路径 |
| LLM 回答 | **不缓存** | — | 每次回答依赖动态上下文，命中率低且可能返回过期医疗建议 |
| 患者病历 | **不缓存** | — | 强一致性要求，直查 PG 用索引（patient_id + record_type）足够快 |
| 嵌入向量 | 内存懒加载 | 进程级 | 避免每次检索重复计算嵌入 |

**核心原则** ★：只缓存"丢了不可惜、错了不危险"的数据。医疗数据宁可慢一点，不可错一点。

### 并发控制：三层防护 ★

| 层级 | 机制 | 保护什么 |
|------|------|----------|
| 入口层 | 令牌桶（60 次/分钟/IP） | 防止单 IP 打爆服务 |
| 数据库层 | PG 连接池（10 + overflow 20） | 防止连接耗尽 |
| 应用层 | 异步线程（审计、记忆抽取） | 热路径不阻塞 |

没有请求级信号量，因为令牌桶下同一 IP 并发已自然受限；若做多租户（多医院），可加按 hospital_id 的并发控制。

### 其他亮点 ★

- **身份认证工具**：`issue_identity_token` / `verify_identity` 两个 MCP 工具，配合 PatientDataGuard 的 token 与 patient_id 一致性校验，形成"工具层也有鉴权"的纵深防御；
- **单一用例数据源**：评估用例统一定义在 `evaluation_cases.py`，避免多副本漂移；
- **Hash 嵌入降级**：ChromaDB 与 torch 都不可用时，用确定性哈希做嵌入——不是最好，但保证系统不崩；
- **Kokoro-82M 本地 TTS**：纯本地语音合成，适合医院内网无外网场景；
- **90 天数据保留策略**：过期数据自动清理，兼顾合规与存储成本。

## 七、面试追问速答 ★★★

| 追问 | 一句话回答 |
|------|-----------|
| ★★★ 为什么不用 LangChain Agent？ | LangChain Agent 默认 ReAct 循环对医疗场景太不可控；我们只需要 plan-then-execute 的确定性路径，自研编排更轻、可审计、可精确控制 LLM 调用次数 |
| ★★ 为什么不直接用 GPT-4？ | 国内医院场景需要合规的国内 API（ModelScope），且主备双模型降级比依赖单一闭源 API 更可靠 |
| ★★ ChromaDB 为什么选它而不是 Milvus？ | 本地嵌入部署、零运维依赖，适合医院内网单机场景，不需要分布式向量库的重武器；未来数据量上来可平滑换 Milvus/pgvector |
| ★★ 记忆抽取的置信度阈值怎么定的？ | 按事件类型分级：关键事件 0.75、会话事件 0.82、业务事件 0.9——业务画像要求最高置信，低了噪音多，高了漏关键信息 |
| ★★★ 安全门会不会误杀正常问题？ | 会的，医疗场景"宁可误杀不可漏过"——误杀了提示用户联系医生，漏过了是真事故 |
| ★★★ 三级分诊和安全门有什么区别？ | 安全门是"不能答"（阻断生成），分诊是"必须引导就医"（升级响应 + 风险提示），一个管禁答、一个管急诊 |
| ★★★ 幻觉检测怎么做？ | LLM 抽取回答中的药物/疾病/检查/症状/治疗实体，与工具返回的患者数据比对，无法确认的实体追加"内容核实提醒"，strict 模式下任何未证实实体都会提醒 |
| ★★ 为什么四路融合而不是单路？ | 语义(58%)覆盖泛化、关键词(22%)保证精确、元数据(12%)科室过滤、时效(8%)优先新数据——单路都有盲区 |
| ★★ trace_id 为什么用哈希存敏感字段？ | 合规要求：可观测系统不能存明文患者 ID，哈希后仍可追溯但无法还原 |
| ★★ 评估为什么只存回答指纹不存原文？ | 评估是质量监控不是内容审计，存 SHA256 足够判断回答变化，不存原文避免隐私泄漏 |
| ★ 如果 Redis 宕机怎么办？ | 自动降级 MockRedisClient（内存 dict），系统仍可运行，只是重启后短期记忆丢失——单次查询无影响 |
| ★ 为什么 TTS 要两个引擎？ | OpenAI 音质好但需外网，Kokoro 本地但音质稍差——双引擎保证内外网环境都能用，自动 fallback |
| ★★★ 照护计划里模型能做什么、不能做什么？ | 能：理解、检索、生成草案、解释；不能：自动发布、修改待办状态、下诊断/剂量/停药指令——临床动作留人工 |
| ★★★ 为什么 LLM 主链路只有 3 次调用？ | 意图识别、规划、回答各 1 次；其他 LLM 点（视觉、改写、幻觉检测、记忆抽取）按需或异步触发，保证延迟可控 |
| ★★ 共识投票为什么不用 LLM 再评一次？ | 投票是统计学问题不是语义问题：序列频次、首工具一致性、意图重叠都是可精确计算的信号，本地算零延迟零成本 |
| ★★★ 怎么防止跨患者数据访问？ | 三层：中间件 token 与 patient_id 一致性校验、工具层身份解析（token 优先覆盖参数）、照护计划 API 的归属校验 + 审计日志留痕 |
| ★ 为什么不用消息队列？ | 同步链路延迟敏感（3s 内），现有异步任务"尽力而为"即可，可靠异步通知出现时再引入 |

## 八、深挖方向（高阶问题准备）★★

以下是面试官可能顺着追问的问题，建议准备：

1. **如果并发从 100 涨到 10000 QPS，哪些点先崩？** 参考答案方向：Redis 单点 → PG 连接池 → LLM API 限流；先做多实例 + 按 hospital_id 分片，再引入队列削峰。
2. **共识投票的权重为什么是 0.35/0.15/0.20/0.05？** 参考答案方向：基于序列一致性的直觉 + 测试调参，欢迎讨论换成 learned weight 或让 LLM 复核低置信候选。
3. **如何证明"plan-then-execute 比 ReAct 好"？** 参考答案方向：延迟与调用次数是可量化指标（3 次 vs N 次），正确性用 131 个测试 + 15 条评估用例 + trace 数据佐证，而非拍脑袋。
4. **多医院多租户改造要动哪些地方？** 参考答案方向：hospital_id 已存在于表结构与 token 中，主要补：按租户的限流/并发控制、知识库元数据隔离、评估看板分区、密钥与模型配置按租户下发。
5. **医疗合规（等保、数据出境）的影响？** 参考答案方向：全链路国内 API、本地 TTS/向量库可内网部署、敏感字段脱敏 + 哈希、审计留痕、90 天保留策略——设计初衷就是可过等保评审。
6. **为什么照护计划的待办状态不做向量记忆？** 参考答案方向：可变任务状态一旦固化成模型记忆会迅速过期且误导回答，正确做法是实时查 PG，记忆只存稳定画像——这也是四层记忆划分的核心理由。
