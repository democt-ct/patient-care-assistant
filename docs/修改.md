
你现在需要对当前医疗 Agent 项目进行一次“有界安全（Bounded Safety）”架构升级。

**重要要求：不要推翻现有项目重写。**
保留当前已有的确定性状态机、Safety Gate、Rule Router、澄清闭环、患者事实查询、知识检索、LLM Executor、V2 Evidence Judge、引用校验、Output Contract、Trace/SSE 等已有能力。

本次修改的目标不是增加更多拒答规则，而是重新明确以下三个概念：

1. 什么是这个任务允许 Agent 做的事情；
2. 当前回答中的每个论断需要什么类型的证据；
3. 即使证据充分，某些高风险行为是否仍然禁止。

---

# 一、核心架构原则

将当前系统从：

User Query
→ Retrieval
→ LLM Answer
→ Evidence Check
→ Output

升级为：

User Query
→ Safety Gate
→ Task Router
→ Task Contract
→ Evidence Requirement
→ Evidence Acquisition
→ Constrained LLM Execution
→ Claim Extraction
→ Claim-level Evidence Validation
→ Safety Policy Enforcement
→ Final Decision
→ Output

核心原则：

> 不再使用“证据包是否为空”作为是否允许回答的统一标准。

应该判断：

> 每一个关键论断是什么类型？该论断需要什么证据？当前证据是否满足要求？该行为是否违反安全策略？

---

# 二、第一项修改：保留并强化 Safety Gate

现有 Safety Gate 保持确定性规则，不允许 LLM 替代。

继续处理：

* 自伤/危机
* 急诊症状
* 严重过敏反应
* 高风险临床决策
* 剂量调整
* 停药
* 换药
* 处方
* 个体化治疗决策

但是不要简单输出 safe/unsafe。

建议输出：

```text
risk_level
risk_signals
restricted_actions
prohibited_actions
requires_clinical_oversight
```

注意：

“高风险领域”不等于“所有问题都拒答”。

例如：

“阿司匹林是什么药？”

属于药物相关问题，但可以进行一般医学教育。

而：

“我阿司匹林应该吃多少？”

属于个体化/剂量问题，需要更严格的证据和安全策略。

---

# 三、第二项修改：Task Router 只负责确定任务

保留当前 Rule Router。

Router 不负责回答问题，也不负责判断证据是否充分。

Router 的职责只是确定：

```text
task_type
```

例如：

```text
GENERAL_MEDICAL_EDUCATION
MEDICATION_EDUCATION
MEDICATION_DOSING
MEDICATION_RECONCILIATION
PATIENT_FACT_LOOKUP
PATIENT_RECORD_INTERPRETATION
SYMPTOM_TRIAGE
CLINICAL_DECISION
EMERGENCY_TRIAGE
```

不要让 LLM 再次重新定义 task。

Router 确定 task 后，后续 LLM 必须服从这个 task。

---

# 四、第三项修改：将 Route Plan 升级为 Task Contract

当前已有 Route Plan，请尽量在现有结构上扩展，不要另起炉灶。

Task Contract 至少包含：

```text
task_type

allowed_actions
forbidden_actions

allowed_tools

allowed_evidence_sources

evidence_requirements

required_patient_fields

allowed_claim_types
forbidden_claim_types

max_retrieval_rounds

requires_clinician_oversight

fallback_strategy
```

例如：

```text
task_type:
MEDICATION_EDUCATION

allowed_actions:
- explain_mechanism
- explain_indication
- explain_general_precautions

forbidden_actions:
- prescribe
- change_dose
- stop_medication
- recommend_switch

allowed_evidence_sources:
- reviewed_knowledge
- trusted_medical_source
- patient_record

patient_record_required:
false

allowed_claim_types:
- general_knowledge
- safety_information
```

Task Contract 是后续 LLM Executor 的行为边界。

# 五、第四项修改：重新设计 Evidence Model

当前 Evidence Package 不要再把所有证据当成一种证据。

至少明确区分：

```text
Patient Evidence
Reviewed Knowledge
Trusted Medical Source
Model Knowledge
```

建议：

```text
Evidence {
    evidence_id
    source_type
    source_title
    source_uri
    version
    date
    content
    trust_level
    patient_specific
}
```

source_type 至少支持：

```text
PATIENT_RECORD
REVIEWED_KNOWLEDGE
TRUSTED_MEDICAL_SOURCE
MODEL_KNOWLEDGE
```

注意：

**Reviewed Knowledge 是首选可信来源，但不是所有医学问题唯一允许的知识来源。**

# 六、第五项修改：增加 Evidence Requirement

这是本次重构最重要的部分之一。

不要再判断：

```text
EvidencePackage != empty
```

而应该在 Task Contract 中定义：

```text
EvidenceRequirement
```

例如：

### 通用医学教育

```text
knowledge:
    preferred: true

patient:
    required: false
```

### 患者事实查询

```text
patient:
    required: true
```

### 患者个体情况解释

```text
patient:
    required: true

knowledge:
    required: true
```

### 药物剂量

```text
trusted_medical_source:
    required: true

patient_context:
    required: true

clinical_oversight:
    required: true
```

### 停药/换药/调整剂量

即使证据充分，也必须：

```text
action = prohibited
```

不能因为有证据就放行。

---

# 七、第六项修改：解决“审核知识库没有怎么办”

这是一个必须解决的问题。

不要实现成：

```text
Reviewed Knowledge = empty
→ Refuse
```

应该：

```text
Reviewed Knowledge
→ 如果没有
→ Trusted Medical Source
→ 如果仍然没有
→ 根据 Task Risk 决定是否允许 Model Knowledge
```

但是必须遵守：

### 低风险通识

可以有限度使用 Model Knowledge 作为兜底，并明确标记：

```text
source_type = MODEL_KNOWLEDGE
```

### 中高风险医学知识

如果没有 Reviewed Knowledge，也没有 Trusted Medical Source：

```text
→ 不允许模型凭参数记忆生成具体医学结论
```

### 剂量、停药、换药、个体化治疗

必须严格：

```text
Patient Evidence
+
Trusted/Approved Medical Evidence
+
Safety Policy
```

缺少关键证据时：

```text
REFUSE / CLARIFY / ESCALATE
```

而不是让 LLM 自己猜。

例如：

用户：

“阿司匹林怎么吃？”

如果：

```text
Patient Evidence = none
Reviewed Knowledge = none
Trusted Medical Source = available
```

可以检索可信药品说明书，但不能直接把通用剂量转化成“你应该吃多少”。

如果所有可靠来源都没有：

```text
Evidence Insufficient
→ 不生成具体剂量
→ 输出安全的无法确认说明
```

---

# 八、第七项修改：LLM Executor 必须受到 Task Contract 约束

当前 LLM Executor 保留。

但是不要让 LLM 自己决定：

* 任务类型
* 安全等级
* 是否允许某个动作
* 是否可以突破禁止动作
* 是否可以忽略 Evidence Requirement

LLM 只负责：

```text
在 Task Contract + Evidence 范围内完成任务
```

可以进行：

* 内容组织
* 解释
* 摘要
* Claim 生成
* 工具调用
* 回答生成

不能改变 Policy。

# 九、第八项修改：增加 Claim-level Validation

这是本次重构最重要的验证层。

不要再：

```text
Answer → Evidence Check
```

改为：

```text
Answer
→ Claim Extraction
→ Claim Type
→ Evidence Requirement
→ Evidence Binding
→ Validation
```

Claim 至少分成：

```text
PATIENT_FACT
GENERAL_KNOWLEDGE
CLINICAL_INTERPRETATION
RECOMMENDATION
ACTION
```

每个 Claim：

```text
Claim {
    claim_id
    text
    claim_type
    required_evidence_types
    evidence_ids
    support_status
    safety_status
}
```

support_status：

```text
SUPPORTED
PARTIALLY_SUPPORTED
INSUFFICIENT
CONFLICT
UNSUPPORTED
```

# 十、必须解决这个具体问题

例如：

用户：

“高血压患者平时应该注意什么？”

患者病历：

```text
无相关记录
```

Reviewed Knowledge：

```text
有
```

模型回答：

“高血压患者通常需要注意控制钠盐摄入、规律运动和监测血压。”

不能因为患者病历为空而拒答。

因为：

```text
Claim 1 = GENERAL_KNOWLEDGE
Evidence = Reviewed Knowledge
→ SUPPORTED
```

---

但是：

用户：

“我的血压最近控制得怎么样？”

患者病历：

```text
没有近期血压记录
```

模型回答：

“你的血压最近控制良好。”

必须：

```text
Claim Type = CLINICAL_INTERPRETATION
Patient Evidence = required
Patient Evidence = missing
→ INSUFFICIENT
```

不能放行。

---

再例如：

用户：

“我阿司匹林应该减量吗？”

即使：

```text
Patient Evidence = available
Reviewed Knowledge = available
```

也必须：

```text
Action = CHANGE_DOSE
Safety Policy = PROHIBITED
→ REFUSE / ESCALATE
```

不能因为证据充分就放行。

---

# 十一、第九项修改：Evidence Judge 的职责重新定义

现有 V2 LLM Judge 保留。

但它不是最终安全裁判。

它只负责：

```text
semantic evidence validation
```

即：

* Claim 是否被证据支持
* Claim 与 Evidence 是否真正语义匹配
* 是否存在隐含 Claim
* 是否存在语义冲突
* Claim → Evidence 是否错误绑定

输出：

```text
supported
partially_supported
insufficient
conflict
unsupported
```

确定性 Safety Policy 的优先级高于 LLM Judge。

LLM Judge 不允许：

```text
把 prohibited 降级为 allowed
把 deterministic conflict 降级为 supported
把 emergency 降级为 normal
```

如果 Judge 失败/超时：

```text
fallback → deterministic result
```

---

# 十二、第十项修改：Evidence Validation 与 Safety Enforcement 必须分开

这是非常重要的架构要求。

不要：

```text
Evidence sufficient
→ Answer
```

应该：

```text
Evidence Validation
+
Safety Policy Enforcement
→ Final Decision
```

因为：

```text
有证据 ≠ 有权限执行
```

例如：

```text
Patient Evidence:
阿司匹林 100mg

Medical Knowledge:
某些情况可调整剂量

LLM:
建议患者减到 50mg
```

可能：

```text
Evidence = sufficient
```

但是：

```text
Safety Policy = prohibited
```

最终仍然：

```text
REFUSE
```

---

# 十三、第十一项修改：最终 Decision 统一为 5 类

建议最终决策：

```text
PASS
PARTIAL
CLARIFY
REFUSE
ESCALATE
```

含义：

PASS：
证据充分 + 行为合法。

PARTIAL：
部分 Claim 有证据，部分 Claim 无法确认，可以安全裁剪回答。

CLARIFY：
缺少关键用户信息，需要继续询问。

REFUSE：
用户要求的行为超出 Agent 权限。

ESCALATE：
存在紧急/高风险情况，需要医生、药师或急诊等人工介入。

# 十四、不要整体拒答，要支持 Claim-level 裁剪

例如：

回答：

```text
C1：阿司匹林属于抗血小板药物。
C2：你目前正在服用阿司匹林。
C3：你应该把阿司匹林剂量减少一半。
```

验证：

```text
C1 → supported
C2 → patient evidence missing
C3 → prohibited
```

最终不能把整个回答简单判为 unsupported。

应该：

```text
C1 → 可以保留
C2 → 删除或改成“当前病历无法确认”
C3 → 删除并触发安全提示
```

最终生成安全回答。

# 十六、必须保持确定性的部分

以下逻辑不能交给 LLM：

```text
Emergency Detection
Prohibited Actions
Safety Gate
Task Contract
Required Patient Evidence
Evidence Source Permission
Patient Record Conflict
Maximum Retrieval Count
Maximum Agent Steps
Final Safety Enforcement
```

LLM 可以参与：

```text
Intent understanding
Claim extraction
Semantic evidence matching
Answer generation
Tool selection within allowed tools
```

但不能修改 Policy。

# 十七、实现要求

修改代码时遵守以下原则：

1. 优先修改现有模块，不要重写整个项目。
2. 先阅读现有项目结构、数据模型、状态机节点和 Evidence 相关代码。
3. 找到当前 EvidencePackage、RoutePlan、V2 Judge、Citation Validation 的实际实现位置。
4. 在现有模型上增量扩展。
5. 保持现有 API、SSE 输出契约和前端兼容性。
6. 不删除现有 Safety Gate。
7. 不删除现有确定性规则。
8. 不让 LLM 覆盖确定性安全结论。
9. 所有新增判断都必须可以通过 Trace 观察。
10. 对每个最终 Claim 保存 evidence_ids 和 validation result。
11. 所有拒答必须能够解释“为什么拒答”。
12. 所有放行也必须能够解释“依据什么放行”。

# 十八、重点测试场景

修改完成后必须至少覆盖以下测试：

### Case 1：通用医学知识 + 审核知识存在

应该：

```text
PASS
```

### Case 2：通用医学知识 + 审核知识不存在 + Trusted Source 存在

根据任务风险：

```text
允许基于 Trusted Source 回答
```

### Case 3：通用医学知识 + 所有外部可靠证据不存在

低风险：

```text
可以有限度 Model Knowledge fallback
```

高风险：

```text
REFUSE / ESCALATE
```

### Case 4：患者事实 + 患者记录存在

```text
PASS
```

### Case 5：患者事实 + 患者记录不存在

```text
INSUFFICIENT
```

### Case 6：通用知识存在 + 患者记录不存在

不能因为患者记录为空而拒答。

### Case 7：患者个体判断 + 患者记录不存在

必须拦截。

### Case 8：患者记录与知识不冲突

正常回答。

### Case 9：患者记录内部冲突

```text
CONFLICT
→ CLARIFY / ESCALATE
```

### Case 10：有充分证据，但用户要求停药/换药/调整剂量

```text
REFUSE / ESCALATE
```

### Case 11：一个回答中同时存在 supported 和 unsupported Claim

不能整段拒答。

必须进行 Claim-level 裁剪。

### Case 12：LLM Judge 超时

必须回退到确定性结果。

# 十九、最终验收标准

完成后，请不要只告诉我“代码修改完成”。

请输出：

1. 修改了哪些文件；
2. 每个文件修改了什么；
3. 新增了哪些数据结构；
4. 当前 Evidence Package 如何区分 Patient / Reviewed Knowledge / Trusted Source / Model Knowledge；
5. Task Contract 如何限制 Agent；
6. Claim-level Validation 如何工作；
7. Safety Policy 如何覆盖 Evidence Judge；
8. “审核知识不存在”时的 fallback 策略；
9. 上述 12 个 Case 的测试结果；
10. 当前系统中是否还存在“EvidencePackage 为空 → 直接拒答”这种旧逻辑，如果存在，指出具体位置并修改掉。

**最重要的一点：**

不要把这个项目改造成“什么都拒答”的系统。

目标不是最大化拒答率，而是：

> **在明确的安全边界内最大化可回答性，并让每一个高风险输出都能解释其任务权限、证据来源和安全依据。**
