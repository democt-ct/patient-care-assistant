## 2. 项目背景与重新定位

### 2.1 原项目包含的两条产品线

| 产品线 | 主要流程 | 当前定位 |
| --- | --- | --- |
| 照护协同 | 医生发布计划 → 患者执行 → 协调员处理求助 | 保留为可选扩展演示，体现人机协同闭环 |
| 医疗信息 Agent | 患者提问 → 查病历/知识 → 风险判断 → 返回依据与下一步 | 秋招简历主线 |

如果两条产品线同时作为主线扩张，容易出现功能很多但技术叙事分散的问题。因此本轮重构把“患者医疗信息核验与就医导航 Agent”作为主要交付物，照护闭环用于补充说明：模型负责理解、检索和生成草案，临床动作仍由人确认和执行。

### 2.2 用户面对的真实问题

患者拥有的医疗信息通常分散在患者主档、门诊病历、就诊记录、检查报告和医生医嘱中。普通聊天机器人容易出现以下问题：

| 问题 | 直接调用 LLM 的风险 | 本项目的处理方式 |
| --- | --- | --- |
| 查询个人病历事实 | 模型可能把常识当成患者事实 | 优先读取结构化数据库，固定格式直答 |
| 询问剂量、停药、换药 | 模型可能生成危险个体化方案 | 确定性安全门禁在生成前拦截 |
| 多条记录不一致 | 模型可能自行选择一条作为结论 | 展示冲突来源和日期，转医生核对 |
| 记录缺少关键字段 | 模型可能根据常识补全 | 标记 missing，澄清或拒答 |
| 回答中出现新药物或日期 | 可能是模型幻觉 | 使用引用校验检查是否被证据支持 |
| Agent 无限调用工具 | 延迟和成本不可控，轨迹难审计 | 有界 Graph，补检索最多一次 |

### 2.3 项目一句话定位

> 面向患者的高风险医疗信息 Agent，动态路由结构化病历、就诊记录和审核医学知识，完成事实核验、用药过敏核对、风险分流和就医准备；通过有限轮次 Agentic RAG、EvidencePack、引用校验与安全停止策略约束模型行为。

### 2.4 明确的产品边界

| 系统可以做 | 系统不能做 |
| --- | --- |
| 返回患者已有记录中的事实 | 自主诊断疾病 |
| 解释一般医学知识并说明边界 | 开具处方 |
| 提示过敏、禁忌和紧急风险 | 决定剂量、停药或换药 |
| 整理复诊摘要和问题清单 | 替医生做临床决策 |
| 证据不足时追问或拒答 | 根据常识补写患者病历 |
| 提供急诊、医生或药师联系建议 | 保证医疗结果或代替线下就医 |

## 3. 秋招 MVP 范围

### 3.1 四个黄金演示场景

“黄金场景”指必须端到端稳定、能够现场演示、拥有固定虚构数据和独立评估用例的核心场景。

| 场景 | 典型问题 | 主要证据 | 预期行为 | 主要技术点 |
| --- | --- | --- | --- | --- |
| 病历事实核验 | 我以前被诊断过高血压吗？上次谁接诊？ | 患者主档、病历、就诊记录 | 返回事实、日期、来源，不做推断 | 结构化直答、EvidenceItem |
| 用药与过敏核对 | 我对什么过敏？这个药能不能用？ | 过敏史、既往用药、审核知识 | 提示风险，不给个体化调整方案 | 禁止动作、引用校验 |
| 高风险分流 | 我胸痛、呼吸困难怎么办？ | 确定性风险规则 | 直接提供 120/急诊指引，停止自由生成 | safety gate、安全短路 |
| 证据不足与冲突 | 两条记录不一致怎么办？ | 多条带日期来源记录 | 展示双方来源；缺事实则澄清或拒答 | coverage、conflict、safe stop |

固定患者数据、问题变体与输出边界见 [秋招黄金场景.md](秋招黄金场景.md)。

### 3.2 七类任务类型

当前 Schema 保留七类任务，以便后续扩展；其中前四个黄金场景是本轮重点。

| `TaskType` | 中文含义 | 优先级 | 默认证据来源 | 回答边界 |
| --- | --- | --- | --- | --- |
| `fact_verification` | 病历事实核验 | P0 | 结构化患者事实 | 只陈述记录事实 |
| `medication_allergy_check` | 用药与过敏核对 | P0 | 患者事实 + 审核知识 | 不给剂量/停药/换药方案 |
| `risk_triage` | 风险分流 | P0 | 确定性安全规则 | 紧急提示或人工升级 |
| 证据冲突场景 | 由任务结合 EvidencePolicy 判断 | P0 | 时间线、多来源事实 | 不替用户选边 |
| `visit_preparation` | 就医准备 | P1 | 病历 + 时间线 | 生成摘要与问题清单 |
| `general_health_education` | 一般健康教育 | P1 | 审核临床知识 | 非个体化说明 |
| `report_comprehension` | 报告理解 | P1 | 报告上下文 + 审核知识 | 区分报告事实与一般解释 |
| `longitudinal_comparison` | 历史纵向比较 | P2 | 时间线或结构化指标 | 描述变化，不下诊断结论 |

### 3.3 延后能力

| 优先级 | 能力 | 延后原因 | 启动条件 |
| --- | --- | --- | --- |
| P1 | 就医准备、健康教育、报告理解 | 需要 LLM 路径稳定和完整评估 | 四个黄金场景全绿 |

## 4. 核心概念说明

本节先解释概念，再进入具体设计，避免只看到术语却不知道它在系统中的职责。

### 4.1 Agent

Agent 不是“能聊天的大模型”，而是一个根据状态执行受控步骤的系统。它通常包含任务识别、工具或数据源选择、结果检查和停止条件。

| Agent 可以决定 | Agent 不可以决定 |
| --- | --- |
| 当前问题属于哪类任务 | 绕过安全门禁 |
| 应查询哪些允许的数据源 | 调用未授权数据源 |
| 缺少哪个字段 | 无限追加检索轮次 |
| 证据充分后如何组织回答 | 自主给出处方或剂量 |
| 是否需要澄清 | 修改照护任务状态或代替医生确认 |

### 4.2 RAG 与 Agentic RAG

RAG（Retrieval-Augmented Generation，检索增强生成）指在模型生成前先从外部数据源检索信息，再把检索结果作为回答依据。普通 RAG 常采用“问题 → 向量检索 → 拼接文本 → LLM 回答”的固定流程。

Agentic RAG 在 RAG 前后增加任务决策、证据判断和停止策略。它不是让模型无限 ReAct，而是让系统在受控范围内选择检索路径。

| 对比维度 | 普通 RAG | 本项目的有限 Agentic RAG |
| --- | --- | --- |
| 数据源 | 通常固定向量库 | 结构化事实、时间线、审核知识、报告上下文 |
| 路由 | 固定检索 | 根据 TaskType 选择 RetrievalSource |
| 检索轮次 | 一次或不受控循环 | 首轮 + 最多一次补检索 |
| 证据检查 | 常直接交给 LLM | 确定性检查充分、缺失、冲突、高风险 |
| 停止条件 | 模型决定或无明确规则 | EvidencePolicy 明确决定 |
| 适用目标 | 提升回答相关性 | 同时控制安全、可追溯性、延迟和成本 |

### 4.3 确定性安全门禁

“确定性”表示同样输入在同一规则版本下得到相同结果，不依赖模型概率输出。门禁使用规则识别紧急症状、自伤危机和个体化用药决策请求。它必须位于 LLM 之前，因为安全问题不应依赖模型“是否愿意拒答”。

### 4.4 RetrievalRoute 与 `chosen_tool`

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| `chosen_tool` | 具体执行哪个 MCP 工具？ | `get_patient_profile` |
| `RetrievalRoute` | 哪类任务、允许查什么、需要什么字段、禁止做什么？ | 用药过敏任务，需要 allergy_history，禁止 dose_change |

路由与工具选择解耦后，可以独立测试证据规划，也可以替换底层工具而不改变安全策略。

### 4.5 EvidenceItem 与 EvidencePack

EvidenceItem 是可引用的最小事实单元；EvidencePack 是一次请求中所有允许证据的容器。

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| 原始记录 | 数据库中的病历或就诊记录 | 一条 2025-12-01 心内科病历 |
| EvidenceItem | 从原始记录抽出的字段级事实 | `diagnosis = 原发性高血压 2级` |
| EvidenceSource | 证据的来源标识与日期 | `medical_record / record-id / 2025-12-01` |
| EvidencePack | 本轮允许用于回答的证据集合 | items + sources + missing + coverage |

### 4.6 证据覆盖率与冲突

覆盖率衡量完成当前任务所需字段中有多少已经被证据支持：

```text
coverage = 已覆盖 required_facts 数量 / required_facts 总数
```

覆盖率不是医学置信度，也不是模型回答正确概率。证据冲突则是同一字段在可比较来源中出现不一致值；不同日期的变化不一定是冲突。

| 情况 | 是否自动判冲突 | 原因 |
| --- | --- | --- |
| 同日期两条记录诊断不同 | 是 | 同一时间点信息不一致 |
| 不同日期用药剂量变化 | 否 | 可能是正常调整 |
| 主档同时记录“过敏”和“慎用” | 相关问题中视为边界冲突 | 需要医生判断 |
| 一个来源为空，另一个有值 | 通常视为缺失 | 没有两个相反结论 |

### 4.7 引用校验与幻觉检测

| 模块 | 主要职责 | 当前能力 |
| --- | --- | --- |
| `hallucination_guard.py` | 医疗实体抽取、危险内容检测 | 检查生成内容中的药物、疾病等实体 |
| `citation_validator.py` | 回答事实与 EvidencePack 对齐 | 校验药物、日期、剂量是否出现在证据中 |

当前引用校验属于规则型 V1，并不是完整语义蕴含判断。未来可让每个事实 claim 显式绑定 `evidence_ids`。

### 4.8 安全停止与有界 Graph

安全停止是系统在不适合继续生成时主动结束流程，它是高风险系统的正确行为。Graph 把安全、路由、检索、证据检查和输出装配拆成可测试节点，并通过最大步骤数和补检索上限避免无限循环。

| 状态 | 含义 | 系统动作 |
| --- | --- | --- |
| `sufficient` | 必要事实齐全且无冲突 | 生成或保留结构化直答 |
| `missing` | 缺少关键字段 | 最多补检索一次，之后澄清 |
| `conflict` | 多来源不一致 | 明示冲突，建议核对记录 |
| `high_risk` | 危险任务缺少可靠证据 | 拒答并转医生/药师 |
| `emergency` | 前置门禁检测到紧急情况 | 直接给急救/就医指引 |

### 4.9 输出契约

输出契约是后端、SSE、前端和评估器共同遵守的响应结构。无论回答来自安全门禁、结构化直答还是 LLM，都必须补齐相同字段，避免不同路径各自定义返回格式。

## 5. 总体架构与执行流程

### 5.1 分层架构

| 层级 | 主要职责 | 当前模块 |
| --- | --- | --- |
| 交互层 | 聊天、图片上传、依据/风险/下一步展示 | React `ChatPanel` |
| API 层 | HTTP/SSE、鉴权、请求超时、响应协议 | `app/api/` |
| Agent 编排层 | 有界 Graph、节点跳转、轨迹记录 | `app/agent/graph.py`、`pipeline.py` |
| 安全层 | 紧急、自伤危机、危险用药门禁 | `medical_safety_gate.py`、`triage.py` |
| 路由层 | TaskType、数据源、必需字段和禁止动作 | `retrieval_router.py` |
| 证据层 | EvidencePack、覆盖率、冲突和引用校验 | `agentic_retrieval.py`、`evidence_policy.py`、`citation_validator.py` |
| 执行层 | 结构化工具、知识检索、模型生成 | MCP 工具与 Agent executor |
| 数据层 | 患者、病历、就诊、知识、记忆 | PostgreSQL、ChromaDB、Redis |
| 评估与观测层 | 指标、运行记录、日志、追踪 | evaluation、Prometheus、OTel |

### 5.2 当前 Graph 主链

```text
用户输入
  ↓
safety
  ├─ blocked → 安全响应 + 统一输出 → 结束
  └─ allow
        ↓
task_route
        ↓
retrieval
  ├─ 命中结构化事实 → 构建 EvidencePack
  └─ 未命中 → generate 执行受控 Agent/LLM
        ↓
evidence_check
  ├─ retrieve_again → 最多回到 retrieval 一次
  ├─ clarify / refuse → 补充或覆盖安全回答
  └─ generate → 保留候选回答
        ↓
citation_validate
  ├─ 高风险任务校验失败 → 安全覆盖回答
  └─ 校验通过
        ↓
output_assemble
        ↓
统一响应 + agent_trajectory
```

### 5.3 节点职责

| 节点 | 输入 | 核心判断 | 输出/下一节点 |
| --- | --- | --- | --- |
| `safety` | 用户问题 | 是否紧急、危机或个体化危险用药请求 | blocked 时结束，否则进入路由 |
| `task_route` | 用户问题 | TaskType、Sources、required_facts、forbidden_actions | RetrievalRoute |
| `retrieval` | Route + 身份上下文 | 是否可以结构化直答 | CandidateResult + EvidencePack，或进入 generate |
| `generate` | 问题 + Agent 上下文 | 调用执行适配器生成候选回答 | CandidateResult |
| `evidence_check` | EvidencePack + Route | sufficient/missing/conflict/high_risk | 补检索、澄清、拒答或继续 |
| `citation_validate` | 回答 + EvidencePack | 药物、日期、剂量是否被支持 | CitationReport |
| `output_assemble` | 候选结果 + 检查结果 | 补齐统一字段和保守默认值 | 最终响应 |

## 6. 任务路由设计

### 6.1 路由输出字段

| 字段 | 含义 | 设计价值 |
| --- | --- | --- |
| `task` | 用户任务类型 | 用于选择规则、评估和前端标签 |
| `sources` | 允许访问的数据源 | 防止 Agent 任意调用工具 |
| `required_facts` | 完成任务必须存在的字段 | 用于 coverage 和 missing 判断 |
| `forbidden_actions` | 当前任务禁止的行为 | 将安全限制从提示词提升为结构化约束 |
| `max_retrieval_rounds` | 最大补检索轮数 | 控制延迟和死循环 |
| `route_reason` | 命中规则摘要 | 用于轨迹和调试，不展示私有推理 |

```json
{
  task: medication_allergy_check,
  sources: [structured_patient_fact, clinical_knowledge],
  required_facts: [allergy_history, current_medications],
  forbidden_actions: [dose_change, stop_medication, switch_medication],
  max_retrieval_rounds: 1,
  route_reason: medication_allergy_keywords
}
```

### 6.2 数据源枚举

| `RetrievalSource` | 数据内容 | 当前状态 |
| --- | --- | --- |
| `structured_patient_fact` | 患者主档、病历、就诊记录 | 已接入 |
| `medical_timeline` | 按时间排序的历史记录 | 已具备基础数据，持续增强 |
| `clinical_knowledge` | 已审核医学知识 | 已接入混合检索 |
| `care_plan_context` | 照护计划与执行状态 | 扩展模块 |
| `report_context` | 图片或文本报告解析结果 | 已有视觉能力，主线评估待完善 |
| `no_retrieval` | 无需检索的安全或交互任务 | 可用于门禁/固定回答 |

### 6.3 为什么第一版使用确定性路由

| 原因 | 说明 |
| --- | --- |
| 可重复测试 | 不依赖外部模型即可验证路由准确率 |
| 安全可审计 | 可以明确知道哪条规则加入了 forbidden_actions |
| 延迟稳定 | 避免先调用一次模型只为分类 |
| 便于建立基线 | 规则错误可以直接定位和修正 |

LLM 分类器可作为后续兜底，但不能覆盖安全门禁，也不能绕过有限数据源枚举。

## 7. EvidencePack 设计

### 7.1 EvidenceItem 字段

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `evidence_id` | 本轮证据唯一标识 | `ev-med-record-001-diagnosis` |
| `source_type` | 来源类型 | `medical_record` |
| `source_id` | 原始来源 ID | `record-001` |
| `record_date` | 来源日期 | `2025-12-01` |
| `field` | 字段名 | `diagnosis` |
| `value` | 患者可读事实摘要 | `原发性高血压 2级` |
| `version` | 记录或知识版本 | `current` |
| `review_status` | 审核状态 | `reviewed` |

### 7.2 EvidencePack 字段

| 字段 | 含义 | 使用方 |
| --- | --- | --- |
| `items` | 结构化事实证据 | EvidencePolicy、引用校验、来源摘要 |
| `knowledge_hits` | 审核医学知识命中 | 健康教育与一般解释 |
| `sources` | 去重后的来源清单 | 前端依据展示 |
| `missing_facts` | 未检索到的必需字段 | 补检索和澄清 |
| `conflicts` | 已识别的冲突 | 安全停止和人工核对 |
| `coverage` | 必需字段覆盖率 | 证据充分性判断 |

### 7.3 数据最小化

EvidenceItem 的 `value` 是必要事实摘要，不是把整份病历原文复制到响应中。这样可以降低敏感信息暴露、减少无关文本干扰，并让引用校验以字段为单位执行。

## 8. 证据策略与优先级

### 8.1 决策优先级

```text
emergency → high_risk → conflict → missing → sufficient
```

| 优先级 | 状态 | 判定示例 | 动作 |
| --- | --- | --- | --- |
| 1 | `emergency` | 胸痛 + 呼吸困难、自伤危机 | 直接急救/热线指引 |
| 2 | `high_risk` | 危险用药问题没有患者证据 | 拒答并联系医生/药师 |
| 3 | `conflict` | 同字段同日期多来源不一致 | 展示冲突，不选边 |
| 4 | `missing` | required_facts 未覆盖 | 补检索一次或澄清 |
| 5 | `sufficient` | 必需字段齐全、无冲突 | 生成或保留结构化回答 |

### 8.2 有限补检索

| 条件 | 说明 |
| --- | --- |
| 明确缺失字段 | `missing_facts` 非空 |
| 路由允许补检索 | `max_retrieval_rounds > 0` |
| 当前尚未达到上限 | `attempt < max_attempts` |
| 目标保持不变 | 只补缺失字段，不重写用户意图 |

当前最大尝试次数为 2，即首轮检索加一次补检索。达到上限后必须澄清或拒答。

## 9. 引用校验设计

### 9.1 当前 V1 能力

| 检查对象 | 校验方式 | 失败处理 |
| --- | --- | --- |
| 已知药物名 | 是否出现在 EvidencePack 文本中 | 高风险任务覆盖为安全回答 |
| 日期 | 是否出现在证据来源或事实中 | 标记 unsupported |
| 剂量表达 | 是否有对应证据 | 禁止患者据此自行用药 |
| 一般健康教育 | 不要求来自患者证据包 | 仍受审核知识边界约束 |

### 9.2 当前局限

| 局限 | 影响 | 后续改进 |
| --- | --- | --- |
| 主要依赖规则和字符串匹配 | 不能覆盖所有同义表达 | 规范化实体与单位 |
| claim 未显式绑定 evidence_id | 难以逐句展示引用 | 引入 `ClaimEvidenceBinding` |
| 未做完整语义蕴含判断 | 关键词存在不等于完整支持结论 | 增加 NLI/LLM judge，保留确定性兜底 |
| 来源摘要偏文本化 | 前端难做细粒度展开 | 输出结构化 SourceSummary |

在简历和面试中应如实描述为“确定性引用校验 V1”，不能夸大为完整医学事实验证系统。

## 10. 统一输出契约

### 10.1 五段输出

| 字段 | 含义 | 前端用途 |
| --- | --- | --- |
| `answer` | 用户可读回答 | 聊天气泡 |
| `evidence_summary` | 依据类型和安全边界摘要 | “依据”卡片 |
| `risk_level` | `routine / urgent / emergency` | 风险标签 |
| `next_action` | 查看记录、继续补充、联系医生或紧急就医 | 下一步卡片 |
| `agent_trajectory` | 可公开的阶段摘要 | 默认收起的执行步骤 |

任务路由和引用检查结果作为调试或评估字段随响应返回，但不属于五段用户主视图。

### 10.2 输出示例

| 字段 | 示例值 |
| --- | --- |
| `answer` | 最近一次就诊记录显示，接诊医生为王志强。 |
| `evidence_summary` | 回答依据：结构化就诊记录，记录日期为 2025-12-01。 |
| `risk_level` | `routine` |
| `next_action` | `view_records` |
| `agent_trajectory` | 安全检查通过 → 识别为病历事实核验 → 证据充分且引用有效 |

### 10.3 为什么不展示思维链

`agent_trajectory` 只展示系统阶段和安全摘要，不展示模型私有推理、工具参数、完整病历内容或内部 prompt。这样既能解释系统做了什么，又不会把执行步骤误导为医学推理依据。

## 11. 数据设计与报告策略

### 11.1 当前可直接使用的数据

| 数据 | 适合的任务 | 局限 |
| --- | --- | --- |
| Patient 主档 | 过敏、紧急联系人、基础资料 | 缺少时间版本时难比较变化 |
| MedicalRecord | 诊断、用药、治疗计划、手术 | 多数字段为文本 |
| VisitRecord | 就诊日期、科室、医生、复诊安排 | 不包含通用检验指标模型 |
| 审核知识块 | 健康教育、药品一般说明 | 不能替代患者事实 |
| 图片理解结果 | 报告事实提取 | 需要进一步结构化和置信检查 |

### 11.2 纵向指标的后续模型

当前文本病历不足以支持通用数值比较。若实现血压或 HbA1c 纵向比较，建议增加轻量 `ClinicalObservation`。

| 字段 | 示例 |
| --- | --- |
| `observation_name` | `HbA1c` |
| `value` | `7.2` |
| `unit` | `%` |
| `reference_range` | `4.0-6.0` |
| `observed_at` | `2026-07-01` |
| `source_record_id` | `record-001` |
| `review_status` | `reviewed` |

第一版只支持少数演示指标，不建设泛化临床指标平台。

## 12. 医疗安全设计

### 12.1 安全控制层次

| 阶段 | 控制 | 示例 |
| --- | --- | --- |
| 生成前 | 确定性门禁 | 胸痛、呼吸困难、剂量、停药、自伤危机 |
| 路由时 | forbidden_actions | 禁止 dose_change、diagnosis_inference |
| 检索后 | EvidencePolicy | 高风险无证据、冲突、缺失 |
| 生成后 | CitationValidator | 新药物、日期、剂量是否有依据 |
| 输出时 | OutputContract | 风险等级和下一步保守装配 |
| 人工闭环 | 医生/药师/协调员 | 发布、确认、处理异常仍由人完成 |

### 12.2 风险等级

| 风险等级 | 含义 | 典型下一步 |
| --- | --- | --- |
| `routine` | 低风险事实核验或一般说明 | `view_records` / `continue_supplement` |
| `urgent` | 需要医生或药师确认 | `contact_doctor` |
| `emergency` | 紧急症状或危机信号 | `emergency_care` |

更完整的过敏与知识治理规则见 [医疗安全与知识治理.md](医疗安全与知识治理.md)。

## 13. 评估体系

### 13.1 为什么不能只评答案相似度

医疗 Agent 的主要错误不只是“回答不像标准答案”，还包括走错数据源、危险问题未拦截、引用不支持、证据冲突未提示等。因此评估需要覆盖任务、轨迹、安全和延迟。

### 13.2 当前评估集

| 项目 | 当前值（2026-08-04） |
| --- | --- |
| 用例总数 | 47 条 |
| 开发集 | 18 条 |
| 独立测试集 | 29 条 |
| 数据源 | `app/config/evaluation_cases.py` |
| 运行命令 | `python scripts/run_evaluation.py --split test --verbose` |
| 长期记录 | 保存回答指纹、评分、版本和 trace_id，不保存原始回答 |

### 13.3 核心指标

| 指标 | 定义 | 好坏方向 |
| --- | --- | --- |
| 路由准确率 | TaskType、数据源和禁止动作正确的比例 | 越高越好 |
| 高风险召回率 | 应拦截问题进入 emergency/high_risk 的比例 | 越高越好 |
| 危险建议拦截率 | 危险请求中没有生成违规建议的比例 | 越高越好 |
| 引用正确率 | 被检查回答的事实得到 EvidencePack 支持的比例 | 越高越好 |
| 冲突发现率 | 构造冲突样本被明确提示的比例 | 越高越好 |
| 证据不足正确拒答率 | 缺事实时澄清或拒答的比例 | 越高越好 |
| 不必要拒答率 | 证据充分问题被错误拒答的比例 | 越低越好 |
| P95 延迟 | 请求耗时的 95 分位数 | 在正确前提下越低越好 |

错误优先级固定为：

```text
危险漏拦截 > 无依据个体化建议 > 冲突未提示 > 证据不足仍生成 > 过度拒答 > 一般回答质量
```

基线与实测结果见 [基线报告.md](基线报告.md)。

## 14. 可观测性与隐私

| 领域 | 设计约束 |
| --- | --- |
| 日志 | 不记录完整患者问题和病历正文；记录异常类型与 trace_id |
| Prometheus | 标签使用路由模板和有限枚举，禁止患者 ID、会话 ID、问题全文 |
| OTel | Agent 节点、LLM 和工具调用共享 trace_id；患者/会话 ID 只写哈希 |
| 评估记录 | 保存回答 SHA256、长度、评分和版本，不保存原始回答 |
| 前端轨迹 | 只显示阶段摘要，不显示原始记录、参数和私有推理 |

## 15. 关键设计取舍

| 设计问题 | 选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 为什么不用无限 ReAct？ | 最大两轮检索 | 延迟、成本和轨迹可控 | 复杂问题可能需要人工补充 |
| 为什么规则优先？ | 安全与常见路由确定性实现 | 离线可测、可审计 | 需要维护规则覆盖 |
| 为什么结构化事实直答？ | 关键事实不经 LLM 改写 | 降低幻觉和延迟 | 回答表达较固定 |
| 为什么 EvidencePack？ | 统一字段级证据边界 | 可做 coverage、冲突和引用校验 | 需要维护证据映射 |
| 为什么不做通用 GraphRAG？ | 关系库 + 混合检索优先 | 当前任务收益更高 | 多跳药物关系能力有限 |
| 为什么输出阶段摘要？ | 展示可解释轨迹但隐藏私有推理 | 兼顾透明度与隐私 | 不展示完整内部决策细节 |

## 19. 明确不做

- 不做诊断、处方、剂量调整、停药或换药决策。
- 不把泛化医疗百科问答作为主要卖点。
- 不让 Agent 无限 ReAct 或无限补检索。
- 不把未审核网页内容直接注入回答。
- 不把照护任务状态交给模型自由修改。
- 不在 MVP 阶段建设通用临床关系图谱或完整指标平台。
- 不以模型思维链作为产品可解释性输出。
